# Contributing to hipsterismo

Thanks for your interest! Bug reports, phone test results, ideas and pull requests are all welcome.

## Reporting a bug or an idea

Open a [GitHub issue](https://github.com/spippoli/hipsterismo/issues/new). For a bug, say what you did, what you expected and what happened, and on Android add the phone model and the app version (*Settings → Apps → Hipsterismo*).

## Testing the app on your phone

If your phone isn't listed in [`android/DEVICES.md`](android/DEVICES.md), the most useful thing you can do is the **5-minute check** in [`android/INSTALL.md`](android/INSTALL.md). It ends with a long-press on the **LIVE** chip, which shares a diagnostic report with no personal data in it. Paste it into a [*Tested phone* issue](https://github.com/spippoli/hipsterismo/issues/new?template=tested-phone.yml), together with any step that didn't go as described.

## Pull requests

The project follows [GitHub Flow](https://docs.github.com/en/get-started/using-github/github-flow): `master` is always releasable, and every change reaches it through a pull request.

1. **Branch** from the latest `master`, with a short kebab-case name prefixed by its purpose: `feat/…`, `fix/…`, `docs/…`, `chore/…`.

   ```sh
   git fetch origin && git switch -c fix/my-change origin/master
   ```

2. **Commit** in small, single-purpose steps following [Conventional Commits](https://www.conventionalcommits.org/): `type(scope): description`, with the types `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `ci`, `build`, `perf`. Add a body when the why isn't obvious, and `!` or `BREAKING CHANGE:` for a breaking change.

   ```text
   fix(android): keep the zoom after switching camera
   ```

3. **Open the pull request** against `master` and describe what changed, why, and how you tested it, with the commands' output where it matters. Link the issue it addresses with `Closes #N`.

## Which tests to run

The commands are in the [README](README.md#tests).

| You changed | Run |
|---|---|
| `src/mosaic/core/` or the native code under `android/` | the core tests, with GCC **and** Clang; `android/scripts/core-on-device.sh`; `./gradlew connectedDebugAndroidTest` |
| Other desktop code under `src/` | the openFrameworks tests (`make -C tests && make -C tests run`) |
| Kotlin code | `./gradlew assembleDebug test connectedDebugAndroidTest` |
| The UI, the camera or the threading | the above, plus the manual checks in [`android/TESTING.md`](android/TESTING.md) |
| Build types, keep rules, or a class the JNI builds or calls | `./gradlew assembleRelease` and `android/scripts/check-release-apk.sh` |

## Rules that are easy to break

- **The core is deterministic.** The same Frame must give the same Mosaic, bit for bit, with GCC and Clang, on x86-64 and arm64; golden hashes check it. Never pass two calls with side effects as arguments of one call or operands of one operator, since their order is unspecified: sequence them in separate statements. Don't rely on the compiler to fuse multiply-adds; write `std::fma` where one is needed.
- **The core includes no openFrameworks, OpenCV or glm header**, so the Android app can build it with only the NDK.
- **Never edit vendored or generated files:**
  - [`src/mosaic/CDT/`](src/mosaic/CDT/) is CDT under the MPL-2.0; to update it, replace every file from a new upstream tag.
  - `src/mosaic/core/AdaptiveLabTable.inc` is generated by `tools/lab-table/generate.cpp`.
  - The launcher icon's drawables are generated by `tools/app-icon/make-icon.py`; edit the script and run it.
- **Every string the user sees is a resource**, with its Italian translation in `values-it/`: a missing one fails the release build.
- **Use the project's words**: Frame, Patch, Contour, Tessel, Mosaic, Grain, as defined in [`GLOSSARY.md`](GLOSSARY.md).

[`CLAUDE.md`](CLAUDE.md) holds the full architecture, build and release notes.
