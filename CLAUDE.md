# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An openFrameworks app that turns a video file (`bin/data/fingers.mov`) or a webcam feed into low-poly "hipster" graphics. In adaptive mode, the default, each frame is segmented into Patches of similar colour, one constrained Delaunay triangulation follows their boundaries, so no triangle crosses two Patches, and each triangle is filled with the mean source colour inside it. The two original modes, spline and stable, are one key press away: each frame gets edge-detected, its contour points are resampled (spline) or snapped to a grid of cells (stable), Delaunay-triangulated, and each triangle is filled with the source colour around its centroid. It can also turn a single image into a Mosaic image from the command line.

An Android app in `android/` (Kotlin, Compose, debug APK for a Pixel 8a) shares the adaptive pipeline's OF-free core through JNI. It opens on a live camera preview of the adaptive Mosaic, with the `min patch area` slider (#64); the shutter or a gallery photo gives a result screen (#65), whose Mosaic can be saved to the gallery or shared as a PNG (#66).

## Build and run

The project must live at `<OF_ROOT>/apps/myApps/hipsterismo`, because the `Makefile` sets `OF_ROOT` to `../../..`.

- Linux/macOS: `make` (or `make Debug` / `make Release`), then `make run`, or run the binary in `bin/` directly. The app loads assets from `bin/data/`.
- Still mode: `bin/hipsterismo [--mode spline|stable|adaptive] IMAGE [OUTPUT]` saves the Mosaic of `IMAGE` to `OUTPUT` (default `IMAGE-mosaic.png`, next to the input) and exits, without showing a window. `--mode` takes any name in `vertexModeNames`. Without it the vertex mode is `vertex_mode` from `bin/data/settings.xml`, or adaptive (`MosaicMaker`'s default) if the tag is missing. The shipped `settings.xml` selects adaptive too. The other parameters always come from `settings.xml`. It renders at the image's own size, and still needs a display for the GL context. `-h`/`--help` prints the usage. Exit code: 0 on success, 1 if the image can't be loaded or saved, 2 on bad arguments (unknown mode or option, `--mode` without a value, missing image, extra arguments), with the error and the usage on stderr.
- IDE projects (Xcode, Visual Studio, VS Code) are not checked in, and `.gitignore` ignores them. Generate them with the openFrameworks projectGenerator: import this folder, and it reads `addons.make`.

Tests for the Mosaic module and the command-line parser live in `tests/`, a windowless OF app built with `ofxUnitTests`. Run them with `make -C tests && make -C tests run`; the process exit code is the number of failed tests. There is no way to run a single test; comment out calls in `run()` in `tests/src/main.cpp`. There is no linter.

The OF-free adaptive core (`src/mosaic/core/`) has its own test executable in `tests/core/`, built with plain CMake and no openFrameworks or OpenCV (it needs only zlib): `cmake -S tests/core -B tests/core/build && cmake --build tests/core/build -j && tests/core/build/core_tests`. The exit code is the number of failed checks. It checks `sizesFor`, that the Tessels tile the Frame, that every Patch is 4-connected and reaches the min (from `segment()`'s labels), that no fallback warning is logged, and the adaptive golden hashes of the three fixtures in `tests/fixtures/` (`fingers.png`'s is the OF suite's adaptive golden) and of a synthetic 2048×1536 still that `upscaled()` makes from `fingers.png` (integer bilinear, so the same on every platform), which covers the photo sizes. It reads the PNGs with its own small zlib decoder (`tests/core/Png.cpp`), so it doesn't need OpenCV's imgcodecs; an optional argument names another fixtures folder. Each hash is printed as a `hash <fixture> 0x…` line. To check another compiler, build into a second folder with `-DCMAKE_CXX_COMPILER=<sdk>/ndk/<version>/toolchains/llvm/prebuilt/linux-x86_64/bin/clang++` (the NDK's host clang, against the system libstdc++): the output must be identical to GCC's. To check the Pixel 8a, run `android/scripts/core-on-device.sh` (see Android app below).

The core's static library (`adaptive_core`, with `-ffp-contract=off`) is defined once, in `src/mosaic/core/CMakeLists.txt`; `tests/core/` and the Android app add that folder with `add_subdirectory()`. It links `Threads::Threads`, for the photo-sized Frames' threads (see Speed under Architecture). The OF makefiles ignore it.

`.gitignore` ignores `tests/core/build*/`. The OF suite, which still links OpenCV, is the oracle for the core's step 1: `testAdaptiveLabMatchesOpenCV` checks `labOf()` against `cv::cvtColor` on all 2²⁴ colours (about a second), and `testAdaptiveKernelMatchesOpenCV` checks `gaussianKernel()` and `gaussianTaps()` against `cv::getGaussianKernel` at the σ of every Frame size up to 4096 px.

### Android app

The Android app lives in `android/`: a Gradle project with the wrapper checked in (Gradle 9.9.1, AGP 9.5.1 with its built-in Kotlin, Compose), JDK 21, NDK r30 (`30.0.16248370`), CMake 3.31.6, compileSdk and targetSdk 37, minSdk 29, arm64-v8a only. It is a debug APK installed by hand; there is no release signing. The toolchain sits under `~/Android` (#52), and nothing is in the shell profile, so set the environment first:

```sh
export JAVA_HOME=~/Android/jdk-21 ANDROID_HOME=~/Android/Sdk
cd android
./gradlew assembleDebug                       # app/build/outputs/apk/debug/app-debug.apk
$ANDROID_HOME/platform-tools/adb install -r app/build/outputs/apk/debug/app-debug.apk
$ANDROID_HOME/platform-tools/adb shell am start -n io.github.spippoli.hipsterismo/.MainActivity
./gradlew test                                # JVM unit tests (app/src/test/), no phone
./gradlew connectedDebugAndroidTest           # instrumented tests, on the connected phone
$ANDROID_HOME/platform-tools/adb logcat -s hipsterismo:I hipsterismo-perf:I hipsterismo-photo:I   # preview fps, core ms, photo times
```

`connectedDebugAndroidTest` uninstalls the app when it ends, which also drops the camera grant: reinstall it afterwards.

Prefer the SDK's `adb` to the distro's `/usr/bin/adb`. `.gitignore` ignores `android/.gradle/`, `android/build/`, `android/app/build/`, `android/app/.cxx/` and `android/local.properties` (not needed when `ANDROID_HOME` is set).

- **Native code:** `app/src/main/cpp/CMakeLists.txt` adds `src/mosaic/core/` (the core's own library and flags, so the floats are the desktop's) and builds `libhipsterismo.so` from `mosaic_jni.cpp`. The core and the glue are compiled at `-O3` in the debug APK too (CDT's asserts stay on there, unlike in the core tests, which build as Release with `-DNDEBUG`; `NDEBUG` would save about 3%). The JNI layer takes a locked ARGB_8888 Bitmap (`NativeMosaic.fromBitmap()`) or a direct RGBA `ByteBuffer` read through a `FrameTransform` (`fromFrame()`; `fromRgba()` is the upright case with a row stride), drops alpha into packed RGB, calls `makeAdaptive()`, and returns a Kotlin `Mosaic`: the `drawVertices` arrays (x, y per vertex, three per Tessel; an ARGB colour per vertex), the Contours as `drawLines` segments (x0, y0, x1, y1; a closed Contour includes its closing segment), the core's `hash()` and `makeAdaptive()`'s time in ms. The JNI checks that the transform's four corners lie inside the buffer and throws `IllegalArgumentException` otherwise. The core's log hook goes to logcat under the tag `Mosaic`.
- **`FrameTransform`** (plain Kotlin, JVM-tested) reads an upright Frame out of a camera buffer: pixel (x, y) is the RGBA at `start + x·xStep + y·yStep`. `FrameTransform.of(width, height, rowStride, pixelStride, rotationDegrees, mirror)` folds in the strides, CameraX's clockwise `rotationDegrees` (90 and 270 swap the size) and, for the front camera, a left-to-right flip after the rotation. So the rotation costs nothing: the glue's copy to RGB walks the steps, and CameraX's own rotation (10–15 ms, #50) stays off.
- **Camera screen** (variant A "Fotocamera" of #57, restyled like the stock Pixel camera app; `MainActivity`, `CameraScreen`, `Controls`):
  - `MainActivity` asks for CAMERA (the only permission) at start. While it is denied, `PermissionScreen` explains why, with a button that asks again, or opens the app's settings after the second refusal; the grant is re-checked on every resume. **The screen stays in portrait** (`screenOrientation="portrait"`), as in the stock camera app: held in landscape, only the icons, the zoom labels and the result's Mosaic turn, by `rememberIconAngle()` (an `OrientationEventListener` through `captureRotationFor()`, the same turns as the shutter's, and `iconAngle()`, which turns the short way). The activity still handles configuration changes itself (`configChanges`), so the camera keeps running.
  - The live Mosaic is shown whole, not cropped (`placement()` fits it, centred, with black bands where the aspect ratios differ); the raw CameraX preview (`PreviewView`, `FIT_CENTER` likewise) shows only until the first Mosaic. The app draws no Contours: `mosaic.contours` still comes from the JNI, but no screen shows it. The LIVE chip shows the fps; a tap adds the core's ms per Frame and the Tessel count (the debug stats overlay of #59).
  - Layout, on black: a 56 dp top bar with the LIVE chip; the 3:4 viewfinder as wide as the screen (shorter on a short screen, so the controls keep 170 dp), with the zoom chips (`ZoomChips`) in a translucent capsule at its bottom; then, where the camera has its mode row, the `min patch area` row (`PatchAreaSelector`: the 8 steps 8…1024 px², default 32, `MinPatchArea`, the selected one centred in a grey pill reading "32 px²", the row fading at the edges; a tap or a swipe picks a step, `selectorOffset()` and `swipedIndex()`); and the round gallery button, the shutter (a white disc in a ring that shrinks while pressed) and the camera switch (`SwitchCameraButton`, whose arrows turn half a turn per tap; an empty box instead on a phone with one camera). The gallery button and the shutter take a photo (below).
  - The row's step survives a configuration change (`rememberSaveable`).
  - **Camera and zoom**, as in the stock camera app: the switch toggles back and front (`PreviewPipeline.switchCamera()` rebinds all three use cases; the front camera's Frames are mirrored, and its photos too, through `ImageCapture.Metadata.isReversedHorizontal`, so they match the preview; CameraX writes that as a mirrored EXIF orientation, which `ImageDecoder` applies). The chips (`zoomPresets()`: the camera's minimum if under 1×, the ultrawide, then 1× and 2× if reached) set the zoom ratio; the lit one (`activePreset()`, the largest at or below the zoom) reads the current ratio (`zoomLabel()`, "1,4×"). A pinch anywhere on the preview zooms freely (`pinch()`, `pinchedZoom()`, from the last ratio asked for, since `ZoomState` lags). The zoom is the camera's, so the analysis Frames, hence the Mosaic, and the photo are zoomed too. The chips show only if the camera can zoom; while a photo is processed the switch, the chips and the pinch are off. The chosen camera survives rotation (it lives in the pipeline); the zoom starts at 1× after a switch.
- **Threading** (`PreviewPipeline`): CameraX 1.6.2 binds Preview, ImageCapture (below) and ImageAnalysis (RGBA_8888, `ResolutionStrategy` 320×240 at 4:3, `STRATEGY_KEEP_ONLY_LATEST`) to the activity's lifecycle, the back camera if there is one, until the switch picks the other (`camera`, a `StateFlow` of `CameraState`: front or back, whether both exist, the zoom and its range from `ZoomState`). One thread, `mosaic-preview` (display priority), runs the analyzer: `FrameTransform` from the image's strides and `rotationDegrees`, `NativeMosaic.fromFrame()`, then the Mosaic goes to a `StateFlow` that the UI draws. The analysis and preview target rotation (not the shutter's, see Photos) follow the display through a `DisplayListener`, also across a 180° turn. On API 31+ an ADPF `PerformanceHintManager` session for that thread gets a 20 ms target and each Frame's work time, so the scheduler keeps it on the X3. The slider's value reaches the thread through a `@Volatile` field and applies from the next Frame.
- **Photos** (#65; `MosaicApp`, `PhotoDecoder`, `PhotoMaths`, `ResultScreen`):
  - `MosaicApp` holds the app's state once the camera is granted (`PhotoState`: `Live`, `Processing`, `Result`) and the slider's step. The shutter (`ImageCapture`, `CAPTURE_MODE_MINIMIZE_LATENCY`, the largest 4:3 size, `targetRotation` following how the phone is held, from an `OrientationEventListener` through `captureRotationFor()`, not the display, so a landscape photo is landscape even with auto-rotate off, and the JPEG's EXIF orientation is right) saves a JPEG to `cacheDir/photos/`, deleted once decoded; `MainActivity` empties that folder at every start. The gallery thumbnail opens the system photo picker (`PickVisualMedia`, images only, no permission).
  - Both go through `PhotoDecoder.decode()`: `ImageDecoder` with `setTargetSize(cappedSize(…))` (2048 px on the long side, aspect kept, the short side rounded; a smaller photo keeps its size), `ALLOCATOR_SOFTWARE`, sRGB as the target colour space (Pixel photos are often Display P3; the core reads sRGB, as on the desktop), and a copy to ARGB_8888 if the decoder gave F16 or 1010102. `ImageDecoder` applies the EXIF orientation itself, and its `info.size` is already upright. Then `NativeMosaic.fromBitmap()` at the slider's value of that moment; `makeAdaptive()` scales the sizes to the photo as in still mode.
  - The photo runs on the preview's own thread (`processPhoto()`), with `paused` set, so the analyzer closes every Frame unprocessed and the thread whose ADPF session keeps it on the X3 does the decode and the core. While it runs, the last preview Mosaic stays frozen and dimmed (`MosaicCanvas(dim = true)`, a colour matrix like the mock's `brightness(.55) saturate(.6)`), the chip reads "in pausa", a ring spins around the gallery button (where the stock camera shows its processing) and every control is disabled. Back does nothing then.
  - The result screen looks like the Google Photos viewer the stock camera opens: the Mosaic whole on black under a top bar (back, the `min patch area` used), with Condividi, Salva and Scarta as glyphs over labels (`BottomAction`) at the bottom. Held in landscape, the Mosaic turns with the glyphs and takes the screen's long side. A photo's Mosaic is final: there is no slider, and it is never recomputed. Scarta and back return to the live preview at once (`paused` off). Condividi and Salva are below.
  - **Photo times:** at the result's first draw one line goes to logcat under `hipsterismo-photo` (`PhotoTiming.line()`): `photo camera|gallery WxH: N ms to the result (capture N, decode N, core N = N%, other N), N Tessels, min patch area N`, from the shutter tap (or the picker's answer) to that draw. The core alone at 2048×1536 (synthetic, from `fingers.png`) takes about 450 ms pinned to the X3 and 420 ms on the X3 and the four A715s (`taskset 100` and `1f0` under `adb shell`), and a 2048 px photo about 510 and 490 ms; before #76 it was 760 and 820 ms on the X3. A 4624×3472 JPEG decodes to 2048 in about 70 ms (A715). In the app, with Thermal Status 0 and the X3 at 2.914 GHz (#76), five camera photos reached the result in 0.93–1.10 s, the core 0.50–0.62 s of it (1.33–1.61 s and 0.95–1.16 s before). Sustained `taskset` runs throttle the X3 even at Thermal Status 0 (its `scaling_max_freq` drops to 1.3–2.4 GHz), and so does the live preview left running over USB charging: check the cap before and after each run.
- **Save and share** (#58, #66; `MosaicExport`, `SaveMaths`, `ExportingResult` in `MosaicApp`):
  - Both make a PNG at the working size (the Mosaic's own, 2048 on the long side or the photo's if smaller), **exactly as the screen draws it**: `MosaicExport.render()` records the same `drawMosaic()` into a `Picture`, renders it through the hardware renderer (`Bitmap.createBitmap(picture)`, as on screen) and copies it to ARGB_8888 for `compress(PNG)`. The render and the encode run on `Dispatchers.Default`; while one runs, Salva and Condividi ignore taps. One `export WxH: N ms` line goes to `hipsterismo-photo` (about 350 ms at 1536×2048 on the phone).
  - **Salva** inserts a MediaStore image (`IS_PENDING` 1, `DISPLAY_NAME` `mosaicFileName()` = `hipsterismo_YYYYMMDD_HHMMSS.png` at the local time of the save, `RELATIVE_PATH` `Pictures/Hipsterismo`, `image/png`), writes the PNG and publishes it; no permission (minSdk 29, the app's own row). On failure the row is deleted and a toast shows. Then the snackbar ("Salvato in Immagini/Hipsterismo", **Apri** = `ACTION_VIEW` on the row's Uri, about 4 s, the mock's `.toast`), and Salva becomes a disabled "Salvato" with a tick for that result (a new photo starts unsaved). Bitmap.compress writes no EXIF, so the PNG has no GPS or camera data (`MosaicExportTest` checks the chunks).
  - **`DATE_TAKEN` is not kept.** The app computes it as #58 says (`mosaicDateTaken()`: the shutter tap for a camera photo; the original's `DATE_TAKEN` from the picker's Uri for a gallery photo, else the picker's answer) and passes it at the insert, but on Android 17 the scan that publishing runs takes `DATE_TAKEN` only from EXIF, so with no EXIF it is NULL afterwards, and an update of it then changes 0 rows (also without `IS_PENDING`). Google Photos then dates the Mosaic at the save. Keeping it would need an EXIF with only `DateTimeOriginal`, which #58's "no EXIF" excludes; see #66's PR.
  - **Condividi** writes the same PNG to `cacheDir/shared/` (emptied first, so at most one file) and sends it through `androidx.core`'s `FileProvider` (`${applicationId}.fileprovider`, `res/xml/file_paths.xml` exposes only `shared/`) with `ACTION_SEND`, `image/png`, `EXTRA_STREAM` and a `ClipData`, read permission granted, inside `Intent.createChooser()`. Nothing goes to the gallery. `MainActivity` empties `cacheDir/shared/` at every start, with `cacheDir/photos/`.

Once a second the screen logs `preview WxH: N fps, core N ms, work N ms, N Tessels, min patch area N` under the tag `hipsterismo`; the first analysis Frame logs its size, strides, rotation and mirroring. On the Pixel 8a (#64): 27–31 fps for 66 s (the camera delivers 30), core 22–24 ms per camera Frame on the X3 (cpu 8). While the screen is locked, a test process sits in the `foreground` cpuset (cpus 0–7, no X3), so `CorePerformanceTest` measures an A715: about 26 ms per `fingers.png` Frame, the first call 60–150 ms (cold).

### Addon dependencies

The app needs these addons in `<OF_ROOT>/addons/` (listed in `addons.make`): ofxCv, ofxDelaunay, ofxGui, ofxMSACore, ofxMSAInterpolator, ofxOpenCv, ofxXmlSettings. Only ofxGui, ofxOpenCv and ofxXmlSettings ship with openFrameworks. Clone the rest yourself:

```sh
cd <OF_ROOT>/addons
git clone https://github.com/kylemcdonald/ofxCv.git
git clone https://github.com/obviousjim/ofxDelaunay.git
git clone https://github.com/memo/ofxMSACore.git
git clone https://github.com/memo/ofxMSAInterpolator.git
git -C ofxDelaunay apply <path-to-this-app>/patches/ofxDelaunay-hull-triangles.patch
```

The patch fixes ofxDelaunay's triangulator, which decides every in-circle test with a rounded circumcentre. A point on a circle through four or more half-pixel points (any axis-aligned rectangle's corners) can then count as inside one of that circle's triangles and outside another, and the new triangles overlap (#39). Triangles with a supertriangle vertex are worse: their circumcircles are huge, so a point on a horizontal border line came out inside the triangle of two other border points and the supertriangle, which added a zero-area triangle; with few other points that wrote past the triangle array, and in large Frames triangles overlapped (#42). The patch decides triangles of real points with the exact sign of the in-circle determinant (on the circle counts as inside), exact for half-pixel coordinates up to about 2600. It treats the supertriangle's vertices as points at infinity: each is `c + R·d` for R → ∞, the orientation and in-circle determinant are polynomials in R, and their signs are those of the leading nonzero coefficients. That also keeps the flat triangles along the convex hull (the Frame border), which upstream's too-small supertriangle dropped. It retires a triangle once the point is past its circumcircle (upstream compared a squared distance with the radius), never one with a supertriangle vertex. And `Triangulate()` stops at the caller's 3·nv triangles, returning 1 with no triangles, and `ofxDelaunay::triangulate()` logs an error, instead of writing past the array. The tests in `tests/` fail without the patch, and they check that every triangulation is proper: it tiles the rectangle, has no zero-area triangles and has 2n − 2 − h triangles. After the patch changes, re-apply it to an existing checkout: `git -C <OF_ROOT>/addons/ofxDelaunay checkout -- libs/Delaunay/src/Delaunay.cpp src/ofxDelaunay.cpp`, then the `git apply` above. Upstream is unmaintained and the code has no free licence, so the fix ships as a patch rather than as a fork or vendored copy.

### openFrameworks version

The app targets openFrameworks 0.12.x on every platform OF supports. It was originally written for OF 0.8 on macOS and has been built and run on Linux (OpenCV 4, C++20).

- `src/mosaic/Mosaic.h` wraps `#include "MSAInterpolator.h"` in a `#pragma GCC diagnostic` block, guarded by `__GNUC__` so it applies to GCC and Clang only. `InterpolatorT::sampleAt()` has no trailing return, and OF's `-Werror=return-type` would otherwise fail the build. OF adds that flag after the project flags, so it can't be overridden in `config.make`.
- ofxCv's `cvtColor`/`GaussianBlur` wrappers changed, so the app calls `cv::cvtColor` and `cv::GaussianBlur` directly.
- Expect a lot of `-Wdeprecated-enum-enum-conversion` warnings from the OpenCV 4 headers under C++20. They are harmless.

### Vendored CDT

Adaptive mode triangulates with [artem-ogre/CDT](https://github.com/artem-ogre/CDT) 2.0.2 (commit `b4413ee`), vendored header-only in `src/mosaic/CDT/`: the 11 headers of upstream's `CDT/include/`, its three licence files (MPL-2.0 for CDT, BSD-3 for `predicates.h`, Apache-2.0 with LLVM exception for `portable_nth_element.hpp`) and a README pinning the version. **Never edit these files**: a modified file would stay under the MPL and its source would have to be offered. To update, replace them all from a new upstream tag and update the README. OF's makefiles add every folder under `src/` to the include paths, so `#include "CDT.h"` works in the app and in the tests with no extra step; don't define `CDT_USE_AS_COMPILED_LIBRARY`. CDT compiles without warnings under OF's flags.

## Architecture

Domain terms (Frame, Contour, Patch, Tessel, Mosaic) are defined in `GLOSSARY.md`.

- **`src/mosaic/` is the Mosaic module**, and all image processing lives there. `MosaicMaker::make(const ofPixels&)` turns a Frame into a `Mosaic`: the Tessels plus the Contours they were built from. `toMesh()` turns a Mosaic into a flat-coloured `ofMesh`. In stable mode `make()` depends on the Frames seen so far, only through which cells are active (see below): the same sequence gives the same Mosaics, `reset()` starts over, and a change of Frame size, cell size or mode resets automatically. In spline and adaptive mode it is a pure function of the Frame. Grayscale and RGBA Frames are converted to RGB. The Tessels always tile the whole Frame rectangle (only an empty Frame gives an empty Mosaic); the tests check this by summing Tessel areas. The tests project compiles this folder directly, so keep the module self-contained in it.
- **Vertex modes.** The int parameter `vertex mode` (XML tag `vertex_mode`; key `s` cycles the modes) picks the pipeline. The values are the `VertexMode` enum in `Mosaic.h` (0 spline, 1 stable, 2 adaptive), and `vertexModeNames` holds their names in the same order, for the panel label, `--mode` and anything else that names a mode. **Adaptive is the default**: a fresh `MosaicMaker` starts in adaptive with `min patch area` 32, so the app and still mode use it whenever `settings.xml` has no `vertex_mode` tag, and the shipped `bin/data/settings.xml` saves `vertex_mode` 2. Tests of spline or stable set the mode explicitly (`SplineMaker`, `StableMaker` in `tests/src/main.cpp`).
- **The spline and stable pipeline inside `make()`:**
  1. Convert to grayscale and blur repeatedly, with odd kernel sizes `1, 3, …, < blur iteration`.
  2. Run Canny, then `ofxCv::ContourFinder`.
  3. Choose vertices, by mode:
     - **Stable** (1): every `cell size` × `cell size` cell a Contour passes through gives one vertex, at a fixed pseudo-random offset inside the cell (hides the grid). A cell stays active for `persistence` Frames after its Contour left. This is what keeps vertices still under camera noise: the stability test on `tests/fixtures/fingers.png` expects ≥ 90% of vertices to stay put between noisy Frames. Tessels take the mean of the 5×5 pixels around their centroid.
     - **Spline** (0, the original look): all Contour points are concatenated into one `msa::Interpolator2D` spline, sampled `interpolation resolution` times (clamped to the Frame, since the spline overshoots where it bridges Contours). Vertices move with every bit of noise. Tessels take the centroid pixel. This mode must keep reproducing the pre-stable output exactly, except where the unpatched ofxDelaunay left holes or overlaps (#39 swapped the diagonal of one cocircular quad on `fingers.png`); the golden test hashes the spline Mosaic of `tests/fixtures/fingers.png` to catch any change.
  4. Add points along the Frame border (corners included), snap every point to a half-pixel grid without duplicates (the triangulation needs distinct points, and spline mode's look depends on the snapping), run Delaunay, drop zero-area triangles, then colour each Tessel as described for the mode.
- **The adaptive pipeline** (mode 2) is an openFrameworks-free core in `src/mosaic/core/AdaptiveCore.{h,cpp}`, namespace `mosaic::core`, which the desktop app shares with the Android app in `android/` (#48, #54, #63). It runs no Canny and no ContourFinder. Its constants (blur σ 0.8, segmentation k 5, boundary ε 3 px) are named in `AdaptiveCore.h`.
  - **The core's interface is plain C++**: `makeAdaptive(RgbImage{data, width, height, stride}, minPatchArea)` returns a `mosaic::core::Mosaic` of Tessels (three `float` Points and an `Rgb`) and Contours (Points plus a `closed` flag; a closed one doesn't repeat its first point). It also has `sizesFor`, `segment()` (steps 1–2 only, a label per pixel, for the tests), `hash()` (the FNV-1a of the goldens) and `setLogHook()`. Logging goes through that hook, stderr by default. **The core includes no openFrameworks, glm or OpenCV header** and links no library but the system's threads (`std::thread`), so the Android app needs only the NDK (#62). `tests/core/` builds it with only its own folder and `CDT/` on the include path, so such an include fails to compile. The lattice and triangle vectors are small structs (`IVec`, `I64Vec`, `DVec`); `dot()` multiplies first and then adds, as glm did. The Lab Frame is a plain float array (`LabFrame`), and the FH distances and Ward means and costs repeat OpenCV's `Vec` arithmetic: sums from 0 in channel order, and a mean as `sum * (1 / n)`. So the floats stayed bit-identical when OpenCV's types went.
  - **Step 1 lives in `AdaptiveLab.{h,cpp}`**, OpenCV's Lab and Gaussian kernel ported exactly:
    - **`labOf()`/`labFrame()`** give OpenCV's float sRGB→Lab bit for bit. OpenCV doesn't evaluate the formula: it interpolates a 33³ table of integer Lab values (built in software floats, so the same everywhere) with integer trilinear weights. The table is `AdaptiveLabTable.inc` (587 KB, Apache-2.0 data from OpenCV 4.10.0), **generated, never edited**: `tools/lab-table/generate.cpp` reads it back from `cv::cvtColor` on the 33³ grid colours, checks that each entry round-trips, and prints it (the build command is in its header). `tools/` is outside `src/`, so neither OF build compiles it.
    - **`gaussianKernel()`** is `cv::getGaussianKernel` bit for bit, including softfloat's `exp` (`softExp()`, a 64-entry table and a polynomial in plain IEEE doubles), so no libm `exp` is involved. `gaussianTaps()` is `GaussianBlur`'s `cvRound(σ·8 + 1) | 1`.
    - **`gaussianBlur()`** is separable, rows then columns, with `BORDER_REFLECT_101`. Each output is the taps in order, accumulated from 0 with `std::fma`, which is correctly rounded, so the floats are the same on every CPU and vector width. `convolve()` has an AVX2 version picked at run time (`__builtin_cpu_supports`), a NEON one on arm64 and a plain loop otherwise; a call to `fmaf` per tap would be several times slower. Each output's fused multiply-adds form one dependent chain, so the vector versions keep 8 registers of sums for consecutive outputs side by side, and the column pass runs in strips of 256 floats so the taps' rows stay in the cache (#76). It differs from `cv::GaussianBlur` in the last bits (OpenCV's order depends on the CPU). That changed the Mosaic of 23 of the 219 Frames of `fingers.mov`, but not of the three fixtures, so **the adaptive golden did not change**.
    - Step 1 takes about 1.4 ms at 320×240, against about 0.8 ms with OpenCV, and about 50 ms at 2048×1536 on the desktop (5 threads; 155 ms before #76).
  - **The desktop adapter** is `adaptiveMosaic()` in `Mosaic.cpp`, called by `MosaicMaker::make()` once the Frame is RGB. It wraps the `ofPixels` as an `RgbImage` (stride from `getBytesStride()`), turns the result back into the desktop `Mosaic` (`glm::vec3`, `ofColor`, `ofPolyline`), and on first use sets the log hook to `ofLog(OF_LOG_WARNING/ERROR, "Mosaic")`, which the tests' `MosaicWarnings` counts. `src/mosaic/Adaptive.h` only re-exports the core's size names (`Sizes`, `sizesFor`, the constants) as `adaptive::…` for the OF code and its tests.
  - **Every size is measured at 320×240** and scaled to the actual Frame by `adaptive::sizesFor(width, height, minPatchArea)`, a pure function with its own tests, so a still image gets the look of the app (#22). `min patch area` is multiplied by W·H / 76 800 (rounded to the nearest, at least 1), and σ and ε by min(W, H) / 240. At 320×240 every factor is exactly 1, so the constants pass through bit for bit; a golden test hashes the adaptive Mosaic of `fingers.png` to catch any change there. FH's k is a colour difference and is not scaled: scaling it by the area ratio moved the counts erratically, and the Ward merge to the scaled min sets the Patch sizes anyway. So the numbers below are for `min patch area` 32 at 320×240. At 1280×960 that becomes 512 px², σ 3.2 and ε 12.
  - **Speed (#76).** The hot spots were rewritten so that every value stays the same, which the goldens and the 2048 px synthetic hash check:
    - `sortedEdges()` writes each row's weights and counts them per bucket, then scatters 8-byte edges (4 · pixel + direction, weight) straight into bucket order, the same stable order as before.
    - `neighbourPairs()` counting-sorts the boundary pairs by their smaller label and sorts each short bucket, instead of `std::sort`-ing every pixel pair.
    - `splitIntoPieces()` joins runs (a row's stretches of one label) with the overlapping runs above, and numbers the pieces by their first run, which is their first pixel's scan order.
    - `traceChains()` finds every crack once into a byte per crack, which also marks it walked.
    - `meanColour()` sums integer runs per row: the vertices are lattice points and the centres half pixels, so on the doubled lattice each edge's side test is an exact integer, and a floor division bounds the run with the same top-left rule.
    - The Lab Frame and the blur's rows are uninitialised arrays, since every value is written before it is read.
    - For Frames of at least 2²⁰ pixels (`parallelPixels`), the Lab, both blur passes and the edge weights split their rows (the column pass its strips) across up to 5 threads, the caller included (`parallelFor()` in `AdaptiveParallel.h`, chunks handed out as threads ask). Each row is computed by the same code on any thread and the bucket counts are integers, so the output doesn't depend on the threads. The scatter, the union-find, Ward, the tracing and CDT stay on the calling thread, and smaller Frames, the live preview among them, run on it alone.
    - At 2048×1536 on the desktop the core went from 590–690 to 310–390 ms (unpinned; 400–470 ms on one core). The FH union-find (100–150 ms) is now the largest step, then the edge sort's scatter (about 40 ms) and Ward 1.
  - **The output must not depend on the compiler**: the golden hash must hold with clang (Android, macOS) as with GCC. Never pass two calls with side effects as arguments of one call or operands of one operator, because their order is unspecified (GCC goes right to left, clang left to right). Sequence them in separate statements. `triangulate()` once built `CDT::Edge(vertex(a), vertex(b))`, and `vertex()` numbers vertices as it first sees them, so clang got other Tessels (#56). Braced init lists, `&&`/`||`/`,` and separate declarators are sequenced and safe. To check with clang on Linux, the NDK's clang++ (`<sdk>/ndk/<version>/toolchains/llvm/prebuilt/linux-x86_64/bin/clang++`) builds host binaries against the system libstdc++. The core tests in `tests/core/` (see Build and run) build with it and must print the same hashes as with GCC. The core's CMake target passes `-ffp-contract=off`, because clang contracts `a*b+c` into FMA wherever the target has it (arm64); OF's makefiles don't, which on x86-64 changes nothing, since its baseline has no FMA. Any FMA the core needs is written out (`std::fma`, or the AVX2/NEON intrinsics in `convolve()`). Built for `aarch64-linux-android29`, the core's only fused instructions are those in `gaussianBlur()`. The OF tests have not been built with clang: OF's makefiles pass `CXX` on to the OF core build, and the core shared by every app was built with GCC.
  1. Convert the Frame to Lab (exactly OpenCV's float conversion, `labFrame()`) and blur it with σ 0.8 (`gaussianBlur()`, deterministic `std::fma`).
  2. Segment it into Patches: Felzenszwalb–Huttenlocher on the 8-connected pixel grid (k 5 in ΔE, min size 1, edges bucket-sorted so the order is deterministic) over-segments it. Neighbouring Patches whose mean colours in the unblurred Frame are exactly equal are joined: the blur turns a sharp edge into one-pixel strips that would otherwise pass `min patch area`, so two flat halves would give several Contours. Then Ward merging (cheapest `n1 n2 / (n1 + n2) |μ1 − μ2|²` first, on 4-neighbours) runs until every Patch has at least `min patch area` pixels. Above about 256 on `fingers.png` it stops changing: the hardest small Patch already reaches min. Because FH links diagonal neighbours, a Patch can still be several pieces that touch only at a pixel corner, and the boundaries (step 3) would give each piece its own Contour and Tessels (#45). So every Patch is then split into its 4-connected pieces, and a second Ward pass absorbs each piece under the min into a neighbour; it only takes merges that involve a small piece, so the Patches that already passed stay as they are. Every Patch is then 4-connected and has at least the min (unless the whole Frame is smaller). Splitting before a single Ward pass instead over-merges: the small pieces keep the global cheapest-first loop running (105 → 65 Patches on `fingers.png`).
  3. Trace the Patch boundaries as crack chains on the lattice of pixel corners, the outside of the Frame counting as one more Patch. Chains run between junctions (corners with three or more cracks, plus the four Frame corners); a junction-free loop is one closed chain. Points where a chain goes straight on are dropped, which keeps the geometry and the shared ends. These are the exact chains.
  4. Simplify each chain once with Douglas–Peucker at ε 3 px, its ends kept, so the two Patches either side of a chain see the same edge. A chain that ends where it starts (a loop, or a chain from a junction back to itself) is split at its point farthest from the start and keeps at least three distinct points. Then the crossing repair: two constraint segments may only meet at a shared end without overlapping, which an exact integer test checks on every pair of nearby segments (binned in 16 px cells; after the first round only pairs involving a chain changed in the last round). Each round, every chain with a conflicting segment, its own or another chain's, is simplified again at half its ε, and below 0.5 px it falls back to its exact chain with every corner, also for a closed loop. The rounds go on until no conflict remains, with no round cap: exact chains never conflict, so every round moves a chain down its finite ladder of ε (3, 1.5, 0.75, exact). The simplified chains are both the constraint edges and the Contours.
  5. Triangulate the whole Frame once with CDT, every simplified chain's segments as constraint edges (`IntersectingConstraintEdges::NotAllowed`, no Steiner points). The repair leaves no conflicts; should CDT still throw, the vertices are triangulated without constraints (still tiling the Frame) and a warning goes to the log hook, so `make()` never throws. The tests check that the warning is not logged on `fingers-060.png` and `fingers-003.png` (Frames 60 and 3, 0-based, of `fingers.mov`), where a repair that simplified closed loops (in the prototypes) or kept only an open chain's ends let CDT throw.
  6. Each Tessel takes the mean colour of the Frame pixels whose centre lies inside it (top-left rule on edges), or the pixel at its centroid if none.
  7. `mosaic.contours` holds the simplified chains off the Frame border: an open `ofPolyline` per chain between junctions, a closed one per loop. The `c` overlay shows them.

  On `fingers.png` (320×240) at `min patch area` 32 this gives 110 Patches, 276 Contours and 1 392 Tessels, in about 12 ms per Frame at -O3; over the 219 Frames of `fingers.mov` about 12.5 ms on average (both about 17 ms before #76). The tests count Patches from the Mosaic as groups of Tessels that no Contour separates (`patchCount()`, built on `patchAreas()`); since every Patch is 4-connected, that is one group per Patch. A group can show less area than its Patch, because the Contours are simplified, so the test that no Patch is a stray piece (#45) asks for at least half the scaled min. On `fingers.png` upscaled ×4 (bilinear), the count goes from 110 to 136, with 2 472 Tessels in about 120 ms (210 ms before #76). With the absolute constants it was 1 077 Patches and 20 571 Tessels. The test allows 40%.
- **Parameters** are the `ofParameterGroup` in `MosaicMaker`. `ofApp` renames it to `panel`, so `bin/data/settings.xml` stays `<panel><first_threshold>…`. A tag's name is the parameter name with spaces replaced by underscores, so renaming a parameter breaks existing settings files: an old `stable_vertices` tag is now ignored.
  - **The panel shows only the active vertex mode's parameters.** `MosaicMaker::parametersFor(mode)` lists them (tested): `vertex mode` first, then the mode's own in group order. Spline hides `cell size` and `persistence`, stable hides `interpolation resolution`, and both hide `min patch area`. Adaptive shows only `vertex mode` and `min patch area` (8–1024 px² at 320×240, scaled with the Frame area; default 32, tag `min_patch_area`). Right after the `vertex mode` slider comes a read-only label with the mode's name; it is not serializable. The one `ofxPanel`, at (0,0), is rebuilt with `gui.clear()` + `gui.add()`: the `vertex mode` listener only sets `panelDirty`, and `update()` rebuilds, so the panel is never cleared during ofxGui's own event dispatch (a drag on the mode slider).
  - **Persistence** never goes through the panel's own `saveToFile`/`loadFromFile`, which only cover the parameters it shows. `ofApp::saveSettings()`/`loadSettings()` `ofSerialize`/`ofDeserialize` the whole group, hidden parameters included. Settings are loaded at startup (and again by `renderStill()`), and the panel header's save and load buttons call the same functions through `savePressedE`/`loadPressedE`, whose listeners return `true` to skip the default.
- **`src/cli/`** holds `parseCommandLine()`, a pure function (no OF) that turns the arguments into a `CommandLine`: window, help, still mode (image, output, and the `--mode` index if given) or an error with exit code 2. It takes the mode names as an argument; `main.cpp` passes `vertexModeNames`, so a new vertex mode is accepted by `--mode` once it is in that list.
- **The tests project** compiles every folder under `src/` (today `mosaic/`, `mosaic/core/`, `mosaic/CDT/` and `cli/`) but not `src/` itself, through `PROJECT_EXTERNAL_SOURCE_PATHS = ../src` plus `PROJECT_EXCLUSIONS = ../src` in `tests/config.make`. OF's makefile supports only one external source path, so don't list folders there; a new folder under `src/` must not depend on `ofApp` or ofxGui.
- **`main.cpp`** calls `parseCommandLine()`. On an error it prints the message and the usage and returns 2. For still mode it sets `ofApp::stillInput`/`stillOutput` (made absolute, because OF resolves relative paths against `bin/data`) and `stillMode`, and opens an invisible window. `ofApp::setup()` then calls `renderStill()`, which reads the parameters from `settings.xml` itself (`loadSettings()`), applies `stillMode` if set, draws the mesh into an `ofFbo`, saves it, and calls `ofExit()` with the exit code.
- **`ofApp`** only gets Frames, calls the Mosaic module, and draws, fitting the Frame in the window with its aspect ratio kept and centred (`OF_SCALEMODE_FIT`). Input selection is compile-time: uncomment `#define LIVE_INPUT` in `ofApp.h` to switch from `ofVideoPlayer` (playing `fingers.mov`) to the camera (320x240, mirrored horizontally). On Linux the camera is opened via `ofGstVideoUtils` with an explicit `v4l2src device=/dev/video0` pipeline, because OF 0.12.1's `ofVideoGrabber` picks the DMABuf caps that GStreamer ≥ 1.24 advertises and fails to link. Other platforms use `ofVideoGrabber` (device 0). The contour overlay draws `mosaic.contours`, and the Delaunay overlay draws the Mosaic mesh as a wireframe.
